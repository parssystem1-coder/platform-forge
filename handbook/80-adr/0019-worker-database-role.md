# ADR-0019: worker نقش دیتابیس جداگانه دارد

## وضعیت

pending review — برخاسته از F-001، F-002

## زمینه

Outbox publisher ذاتاً بین‌مستاجری است: باید رخداد همه مستاجرها را بردارد. اما معماری می‌گوید هر دسترسی درون tenant context است. پروژه این تناقض را حل نکرده بود و نتیجه عملیش این بود که دو جدول outbox کلاً بدون RLS ماندند.

## تصمیم

نقش سوم: `platform_worker`.

| نقش | دسترسی |
| --- | --- |
| `platform_migration` | مالک schema، فقط migration |
| `platform_app` | فقط مستاجر جاری، روی همه جداول |
| `platform_worker` | بین‌مستاجری، فقط روی `outbox_events`، `outbox_dead_letters`، `processed_events` |
| `platform_readonly` | SELECT، زیر RLS |

مزیت امنیتی اصلی: اگر API کامپرومایز شود، مهاجم credential بین‌مستاجری ندارد. در مقابل گزینه «RLS را روی outbox نگذاریم»، این بینهایت بهتر است.

## پیامد منفی

- یک credential بیشتر در مدیریت رمز، و یک مورد بیشتر در رانبوک چرخش کلید.
- worker نمی‌تواند مستقیماً Use Caseی را که به جداول مستاجر می‌نویسد با همان اتصال اجرا کند؛ باید با اتصال app و `withTenant` این کار را بکند. این دقیقاً رفتار مطلوب است.

## شرط بازبینی

اگر تعداد workerهای بین‌مستاجری از دو گذشت، باید برای هر کدام نقش جدا با grant حداقلی بررسی شود.
