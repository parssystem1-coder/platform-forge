# ADR-0020: شماره سفارش در دیتابیس تولید می‌شود

## وضعیت
pending review — برخاسته از F-028

## زمینه
`orders` قید `UNIQUE (tenant_id, number)` دارد، اما هیچ سندی نمی‌گوید این شماره کجا ساخته می‌شود. حدس طبیعی هر توسعه‌دهنده، `max(number) + 1` در اپلیکیشن است، که تحت بار همزمان قطعاً برخورد می‌دهد، و بدترین جای ممکن برای این خطا، لحطه پرداخت است.

## تصمیم
جدول شمارنده به ازای مستاجر با افزایش اتمیک:

```sql
CREATE TABLE tenant_counters (
  tenant_id uuid NOT NULL,
  counter_key text NOT NULL,
  next_value bigint NOT NULL DEFAULT 1,
  PRIMARY KEY (tenant_id, counter_key)
);

-- اتمیک، در یک دستور، بدون خواندن قبلی
UPDATE tenant_counters SET next_value = next_value + 1
 WHERE tenant_id = $1 AND counter_key = 'order_number'
RETURNING next_value - 1 AS value;
```

همان الگوی `quota_counters`. شماره قابل خواندن می‌ماند، که برای پشتیبانی تلفنی مهم است. خلاف uuid که مشتری نمی‌تواند در تلفن بخواند.

## پیامد منفی
- یک ردیف داغ به ازای مستاجر: سریال‌سازی در لحطه ثبت سفارش. تا چند ده سفارش در ثانیه برای یک مستاجر مسئله‌ای نیست.
- شماره‌ها در صورت rollback تراکنش ممکن است سوراخ داشته باشند. پذیرفتنی است، مگر الزام مالیاتی پیوستگی بخواهد.

## شرط بازبینی
اگر قانون مالیاتی بازار هدف، شماره فاکتور پیوسته و بدون سوراخ بخواهد، این الگو باید به تخصیص پس از COMMIT موفق تغییر کند.
