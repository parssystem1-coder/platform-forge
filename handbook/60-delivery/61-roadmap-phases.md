# ۶۱. فازبندی

## ۶۱.۱ منطق ترتیب

ترتیب قبلی زیادی control-plane heavy بود: Commerce فاز ۹.
ترتیب جدید بر اساس یک سوال چیده شده:

> نزدیک‌ترین کار به درآمد واقعی که باید قبلش بسازیم چیست؟

---

## ۶۱.۲ نقشه فازها

| فاز | عنوان | خروجی قابل نمایش | تخمین |
| ----- | ------- | --------------------- | ------- |
| ۰ | Foundation | مخزن، CI، compose، kernel، مرزهای اجبارشده | ۱ هفته |
| ۱ | Identity + Tenancy + AuthZ | ثبت‌نام تا ورود و سوییچ Tenant | ۲ تا ۳ هفته |
| ۲ | Commerce MVP | محصول، فروشگاه، سبد، سفارش | ۴ تا ۶ هفته |
| ۳ | Notifications + Workers | ایمیل تراکنشی، کارهای پس‌زمینه | ۱ تا ۲ هفته |
| ۴ | Features و پلن حداقلی | گیت قابلیت واقعی | ۲ هفته |
| ۵ | Billing + Ledger | پرداخت واقعی و فاکتور | ۳ تا ۴ هفته |
| ۶ | Metering + Quota | سقف واقعی و مصرف | ۲ هفته |
| ۷ | Domains + Public API | دامنه اختصاصی، API key، webhook | ۳ هفته |
| ۸ | AI Gateway | یک جریان AI واقعی | ۲ هفته |
| ۹ | Automation | جریان کار داخلی | ۲ هفته |
| ۱۰ | MCP | ابزار برای ایجنت | ۲ هفته |
| ۱۱+ | CRM / SEO / Accounting | دامنه‌های جدید | پروژه جداگانه |
| ۱۲+ | Plugins و Marketplace | اکوسیستم | پروژه جداگانه |

تخمین‌ها برای یک تیم ۲ تا ۳ نفره بک‌اند است. با یک نفر، ضرب در ۲ کن.

---

## ۶۱.۳ مرزهای برش عمودی

هر فاز باید یک قابلیت کامل بدهد، نه یک لایه.

```text
غلط: فاز ۱ فقط دیتابیس، فاز ۲ فقط API، فاز ۳ فقط UI
درست: فاز ۱ ثبت‌نام کامل از فرم تا دیتابیس تا ایمیل
```

دلیل: لایه‌ای کار کردن باعث می‌شود تا فاز آخر نفهمی طراحی غلط بوده.

## ۶۱.۴ شرط ورود هر فاز

| فاز | فقط وقتی شروع کن که |
| ----- | -------------------- |
| ۲ | فاز ۱ DoD سبز باشد و تست نشتی مستاجر کامل باشد |
| ۴ | حداقل ۳ پلن واقعی با قیمت مشخص تعریف شده باشد |
| ۵ | درگاه پرداخت انتخاب و حساب باز شده باشد |
| ۶ | حداقل یک منبع واقعاً محدود وجود داشته باشد |
| ۸ | یک مشتری واقعی قابلیت AI را خواسته باشد |
| ۱۰ | API عمومی حداقل ۱ ماه پایدار باشد |
| ۱۲ | ۳ افزونه شخص ثالث واقعی درخواست شده باشد |

## ۶۱.۵ دام‌هایی که تیم‌ها درشان می‌افتند

| دام | نشانه هشدار |
| ----- | -------------- |
| ساخت موتور Entitlement قبل از فروش | پلن‌ها هنوز فرضی هستند |
| ساخت Plugin API قبل از ماژول واقعی | هیچ مصرف‌کننده واقعی ندارد |
| ساخت MCP زودهنگام | API هنوز در حال تغییر است |
| مهاجرت زود به Microservice | درد واقعی ثبت‌شده‌ای وجود ندارد |
| اتوماسیون با n8n از روز اول | منطق کسب‌وکار به جایی می‌رود که تست ندارد |

## ۶۱.۶ معیار توقف و بازنگری

اگر در پایان فاز ۲ این موارد محقق نشد، معماری را بازبین کن نه فاز بعد را شروع:

- یک مشتری واقعی بتواند محصول بسازد و سفارش بگیرد
- p95 صفحه محصول در بودجه باشد
- هیچ نشتی بین دو Tenant وجود نداشته باشد
