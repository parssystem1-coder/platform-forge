# ۱۴. Realm های هویت

> اگر فقط یک فایل را قبل از طراحی دیتابیس می‌خوانی، این باشد. این اشتباه قابل برگشت نیست.

## ۱۴.۱ مسئله

در یک پلتفرم E-Commerce چندمستاجری، دو موجود کاملاً متفاوت وجود دارد که هر دو اسمشان «کاربر» است:

1. کسی که فروشگاه را مدیریت می‌کند
2. کسی که از فروشگاه خرید می‌کند

اگر این دو در یک جدول باشند، مشکلات زیر اجتناب‌ناپذیر می‌شوند:

| مشکل | توضیح |
| ------- | -------- |
| تعارض ایمیل | یک ایمیل می‌خواهد هم در فروشگاه A خریدار باشد هم در فروشگاه B، با رمز متفاوت |
| نشت حریم خصوصی | فروشگاه A نباید بفهمد این شخص مشتری فروشگاه B هم هست |
| افزایش سطح دسترسی | اگر خریدار و کاربر هم‌جنس باشند، یک باگ Membership می‌تواند خریدار را ادمین کند |
| تورم جدول | جدول users با میلیون‌ها خریدار، ولی فقط هزار کاربر پلتفرم |
| اختلاف الزامات امنیتی | کاربر پلتفرم به MFA اجباری نیاز دارد، خریدار حتی ممکن است رمز نخواهد |

---

## ۱۴.۲ تصمیم: چهار realm مستقل

```text
+---------------------------------------------------------------+
|                     PLATFORM IDENTITY REALM                   |
|  users (global) -> memberships -> tenants                     |
|  مالک، ادمین، کارمند کسب‌وکار                          |
|  MFA اجباری برای نقش owner، نشست مدیریت‌شده           |
+---------------------------------------------------------------+

+---------------------------------------------------------------+
|                    PLATFORM STAFF REALM                       |
|  staff_users (تیم خودِ ما)                                   |
|  جدا، با MFA اجباری، امکان impersonation ثبت‌شده          |
+---------------------------------------------------------------+

+---------------------------------------------------------------+
|                  STOREFRONT CUSTOMER REALM                    |
|  customers (tenant_id اجباری)                                |
|  unique (tenant_id, email)  <-- کلید ماجرا                   |
|  پشتیبانی از guest checkout، بدون رمز                     |
+---------------------------------------------------------------+

+---------------------------------------------------------------+
|                    MACHINE CLIENT REALM                       |
|  api_clients + api_keys (tenant-scoped) / oauth clients        |
|  با scope، بدون نشست انسانی                              |
+---------------------------------------------------------------+
```

## ۱۴.۳ جدول تفاوت‌ها

| ویژگی | Tenant User | Shopper (Customer) |
| -------- | ------------- | -------------------- |
| دامنه یکتایی ایمیل | کل پلتفرم | درون یک Tenant |
| می‌تواند چند Tenant داشته باشد | بله، با Membership | نه، رکورد جدا در هر Tenant |
| مدل دسترسی | Role و Permission | مالکیت رکورد |
| MFA | اجباری برای owner | اختیاری |
| طول عمر نشست | کوتاه، چرخشی | بلندتر، راحت‌محور |
| حساب بدون رمز | ممنوع | مجاز (guest) |
| حذف حساب | مربوط به Membership | حق فراموشی برای هر Tenant جدا |
| در RLS | جدول platform-wide | جدول tenant-bound |

## ۱۴.۴ مدل مفهومی Customer

```text
customers
  id
  tenant_id            <- اجباری، در کلید یکتا هم می‌آید
  email                <- unique(tenant_id, email)
  email_verified_at
  password_hash        <- nullable برای guest
  phone
  display_name
  marketing_consent_at <- مهم برای GDPR
  status               <- guest | active | blocked
  created_at, updated_at
```

### مسیر تبدیل guest به حساب دارنده رمز

```text
guest checkout
  -> customer با status=guest و بدون password_hash
  -> سفارش به همین customer متصل می‌شود
  -> بعداً دعوت برای ساخت رمز
  -> تعیین رمز و تأیید ایمیل
  -> status=active
```

مزیت: تاریخچه سفارش از دست نمی‌رود و مجبور به merge پیچیده نیستی.

## ۱۴.۵ مدل دسترسی خریدار

خریدار Permission ندارد. مالکیت دارد.

```ts
// غلط
authorize(customer, 'commerce.order.read', { tenantId })

// درست
assertOwnership(customer.id, order.customerId)
```

در عمل مسیر خریدار این است:

```text
Customer session
  -> tenant از دامنه تشخیص داده می‌شود (نه از header دلخواه)
  -> customer_id از نشست
  -> هر query با tenant_id و customer_id محدود می‌شود
  -> RLS پشتوانه نهایی
```

> در مسیر فروشگاه، `X-Tenant-Id` از سمت کلاینت پذیرفته نمی‌شود. Tenant فقط از نگاشت دامنه می‌آید.

## ۱۴.۶ impersonation توسط تیم پشتیبانی

این قابلیت فاز پایین‌تری است، اما قراردادش از امروز مشخص است:

- فقط Platform Staff
- فقط با دلیل ثبت‌شده
- فقط محدود به زمان کوتاه
- در تمام Audit ها با `impersonated_by` مشخص
- هرگز بدون اطلاع به Tenant Owner

اگر این قالب را از اول نگذاری، بعداً پشتیبانی با رمز مشتری کار می‌کند. و این فاجعه است.

---

## ۱۴.۷ معیار پذیرش

- دو جدول جداگانه وجود دارد: `users` و `customers`
- `customers` کلید یکتای مرکب `(tenant_id, email)` دارد
- نشست خریدار و کاربر در دو جدول جدا و با کوکی متفاوت مدیریت می‌شوند
- تست: خریدار با همان ایمیل در دو Tenant مجاز و مستقل است
- تست: نشست خریدار هرگز به API پنل دسترسی ندارد
- تست: تعویض `X-Tenant-Id` در مسیر فروشگاه بی‌اثر است
