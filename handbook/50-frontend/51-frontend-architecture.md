# ۵۱. معماری فرانت‌اند

## ۵۱.۱ چهار سطح متفاوت

این چهار تا الزامات کاملاً متفاوتی دارند و نباید یکسان ساخته شوند:

| سطح | رندر | اولویت | دامنه |
|------|------|--------|-------|
| Marketing | SSG | SEO و سرعت | platform.com |
| Storefront | ISR + SSR | SEO و تأخیر | myshop.com |
| Tenant Admin | SPA (CSR) | قابلیت و دقت | myshop.platform.com/admin |
| Platform Admin | SPA (CSR) | قدرت و امنیت | admin.platform.com |

### چرا پنل SPA است و فروشگاه نیست

- پنل: پشت لاگین، SEO بی‌معنی، تعامل سنگین، حالت محلی زیاد
- فروشگاه: SEO حیاتی، ترافیک بالا، محتوای قابل کش

قاطی کردن این دو در یک الگو، یا فروشگاه را کند می‌کند یا پنل را پیچیده.

---

## ۵۱.۲ ساختار

```text
apps/web/
  app/
    (marketing)/          platform.com
    (storefront)/         دامنه مشتری
    (admin)/              پنل Tenant
    (platform-admin)/     پنل داخلی
  middleware.ts           تشخیص دامنه و نگاشت Tenant

packages/ui/              دیزاین سیستم مشترک
packages/sdk/             کلاینت تایپ‌دار تولیدشده از OpenAPI
```

### قاعده طلایی SDK

کلاینت از OpenAPI **تولید** می‌شود، دستی نوشته نمی‌شود.
اگر دستی بنویسی، در ماه سوم فرانت و بک دو قرارداد متفاوت دارند و هیچ‌کس خبر ندارد.

## ۵۱.۳ مدیریت حالت

| نوع حالت | ابزار |
|-----------|-------|
| داده سرور | TanStack Query |
| فرم | React Hook Form + Zod |
| حالت UI محلی | useState و useReducer |
| حالت کلی سبک | Context یا Zustand |

ممنوع: ریختن داده‌ی سرور در یک store کلی. این دقیقاً همان جایی است که همگام‌سازی دردناک می‌شود.

## ۵۱.۴ مدیریت توکن در فرانت

```text
access token   در حافطه (نه localStorage)
refresh token  کوکی HttpOnly (فرانت نمی‌بیند)
```

منطق تمدید:

```text
درخواست با 401
  -> تلاش refresh (یک بار، با قفل درون‌مرورگری)
  -> موفق: تکرار درخواست
  -> ناموفق: پاک‌سازی حالت و هدایت به ورود
```

قفل لازم است، وگرنه ۱۰ درخواست همزمان ۱۰ بار refresh می‌زنند و چرخش توکن خودت را قفل می‌کنر.

## ۵۱.۵ مدیریت خطا

هر کد خطای problem+json باید به یک واکنش UI نگاشت شود:

| کد | واکنش UI |
|-----|-----------|
| `identity.invalid_credentials` | خطای زیر فرم |
| `identity.mfa_required` | نمایش مرحله کد دومرحله‌ای |
| `identity.email_not_verified` | صفحه ارسال مجدد تأیید |
| `billing.feature_not_available` | کارت ارتقای پلن |
| `billing.quota_exceeded` | نمایش میزان مصرف و دکمه ارتقا |
| `authz.forbidden` | پیام دسترسی و تماس با مدیر |
| `common.rate_limited` | شمارش معکوس تا تلاش مجدد |

> این جدول مهم‌تر از چیزی است که به نطر می‌رسد. تفاوت `402` و `403` در UI مستقیماً درآمد است.

## ۵۱.۶ سه بعدی و جلوه‌های بصری

تصمیم: مجاز فقط در صفحه فرود و نمایش محصول، با سه شرط:

1. بارگذاری تنبل، هرگز در باندل اولیه
2. جایگزین ایستا برای دستگاه ضعیف و `prefers-reduced-motion`
3. هرگز در پنل ادمین

پنل باید سریع، سبک و در دسترس باشد. جلوه بصری در پنل فقط هزینه است.
