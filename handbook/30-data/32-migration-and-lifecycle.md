# ۳۲. مهاجرت و چرخه عمر داده

## ۳۲.۱ قواعد مهاجرت

1. مهاجرت‌ها SQL صریح و تغییرناپذیرند. مهاجرت مرج شده را ویرایش نمی‌کنیم.
2. هر مهاجرت باید با نسخه قبلی کد سازگار باشد (backward compatible).
3. تغییر شکستننده با الگوی دومرحله‌ای انجام می‌شود.
4. هر جدول tenant-bound باید در همان مهاجرت سیاست RLS بگیرد.

### الگوی دومرحله‌ای برای تغییر شکستننده

```text
مرحله ۱ (expand)
  ستون جدید nullable اضافه می‌شود
  کد هم قدیم هم جدید را می‌نویسد
  دیپلوی

مرحله ۲ (backfill)
  job داده قدیمی را پر می‌کند

مرحله ۳ (contract)
  ستون اجباری می‌شود
  کد فقط جدید را می‌خواند
  ستون قدیمی حذف می‌شود
```

هرگز هر سه مرحله در یک دیپلوی.

## ۳۲.۲ عملیات خطرناک در Postgres

| عملیات | ریسک | راه امن |
|-------|------|----------|
| `ALTER TABLE ... ADD COLUMN NOT NULL DEFAULT` | قفل طولانی در نسخه‌های قدیم | افزودن nullable و سپس backfill |
| `CREATE INDEX` | قفل نوشتن | `CREATE INDEX CONCURRENTLY` |
| تغییر نوع ستون | بازنویسی کل جدول | ستون جدید و مهاجرت تدریجی |
| افزودن FK روی جدول بزرگ | اسکن کامل | `NOT VALID` و سپس `VALIDATE CONSTRAINT` |
| `DROP COLUMN` | شکست نسخه قبلی کد | فقط در مرحله contract |

همه‌ی مهاجرت‌ها با `lock_timeout` و `statement_timeout` محدود اجرا می‌شوند.

## ۳۲.۳ نقش‌های دیتابیس

```sql
-- مالک ساختار، فقط مهاجرت
CREATE ROLE platform_owner LOGIN PASSWORD '...';

-- نقش اجرای اپلیکیشن
CREATE ROLE platform_app LOGIN PASSWORD '...';

-- کلیدی: نه مالک است، نه BYPASSRLS دارد
GRANT SELECT, INSERT, UPDATE, DELETE ON ALL TABLES IN SCHEMA public TO platform_app;
ALTER DEFAULT PRIVILEGES IN SCHEMA public
  GRANT SELECT, INSERT, UPDATE, DELETE ON TABLES TO platform_app;
```

> مهم‌ترین اشتباه رایج: اجرای اپلیکیشن با نقش مالک. در این حالت RLS دور زده می‌شود و کل نمایش امنیتی تو تزئینی است.

## ۳۲.۴ چرخه عمر داده

```text
داده:  created -> active -> archived -> retention -> deleted
Tenant: active -> suspended -> canceled -> grace -> archived -> purged
```

### سیاست نگهداری پیشنهادی

| داده | مدت |
|------|------|
| Audit log | ۲ سال |
| Usage event خام | ۱۳ ماه |
| Outbox منتشرشده | ۷ روز در جدول اصلی |
| فاکتور و دفتر مالی | دائمی (الزام قانونی) |
| نشست منقضی | ۳۰ روز |
| داده Tenant لغوشده | ۹۰ روز مهلت، سپس آرشیو |

### حق فراموشی

درخواست حذف داده‌ی یک خریدار باید:
- داده شخصی را بی‌نام کند
- رکوردهای مالی را حفظ کند (الزام قانونی)
- در Audit ثبت شود

یعنی حذف واقعی رکورد نیست، بلکه بی‌نام‌سازی است. این را از اول در مدل داده در نطر بگیر.

## ۳۲.۵ پشتیبان و بازیابی

| مورد | سیاست |
|------|--------|
| پشتیبان کامل | روزانه |
| WAL مستمر | برای PITR |
